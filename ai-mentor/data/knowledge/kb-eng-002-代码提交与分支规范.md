## 分支模型

| 分支 | 用途 | 生命周期 |
|---|---|---|
| `main` | 随时可发布 | 长期 |
| `release/*` | 发布准备 | 一个版本 |
| `feat/*`、`fix/*` | 日常开发 | 合并即删 |

命名示例：`feat/ORD-1024-优惠叠加`、`fix/ORD-1101-地址校验兼容`。

## 提交信息

格式：`类型(范围): 做了什么`

- 类型：`feat` / `fix` / `refactor` / `docs` / `test` / `chore`
- 范围：模块名，如 `order`、`user`
- 一行说清做了什么，不要写"修改代码"、"update"

## 提交前自检清单

- [ ] 本地跑通了相关测试
- [ ] 没有提交调试用的 `console.log` / `print` / 临时开关
- [ ] 没有提交密钥、Token、内网地址
- [ ] 变更范围与 PR 描述一致，没有夹带无关改动

## 代码评审（PR）

1. PR 描述必须写清：**改了什么、为什么改、怎么验证、风险是什么**。
2. 单个 PR 控制在 **400 行以内**，超过请拆分，否则评审质量会急剧下降。
3. 评审意见必须在 **1 个工作日内** 响应，不同意也要回复理由，不要沉默。
4. 有分歧时当面或语音对齐 15 分钟，不要在评论里来回写小作文。

## 关于"夹带改动"

顺手改的格式、重命名的变量、升级的依赖，都会让评审人无法判断风险。请单独开一个 PR。
