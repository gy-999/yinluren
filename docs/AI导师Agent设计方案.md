# 引路人 · AI 导师 Agent 设计方案

> 版本 v1.0 ｜ 定位：把新人培养中"导师被重复消耗"的部分交给一个可持续沉淀的小工具
> 交付物：本文档 + `ai-mentor/` 可运行 MVP（本地 Web 界面，纯标准库，零安装）

---

## 1. 背景：导师那句话里的真实需求

导师说"每一届都培养太麻烦了"。他烦的**不是回答问题**，是**重复劳动**。
而重复劳动有 5 种，问答只是其中最显眼的一种：

| 重复劳动 | 新人侧表现 | 导师侧消耗 | 重复度 |
|---|---|---|---|
| 信息传递 | 同一批问题问一百遍 | 答案型回答 | ★★★★★ |
| 路径规划 | 不知道先学什么、学到什么算过关 | 反复讲培养计划 | ★★★★ |
| 陪练反馈 | 没人陪着练、没人点评 | 逐句改、逐行 review | ★★★★ |
| 进度追踪 | 卡住了不敢说 | 挨个问"你到哪了" | ★★★ |
| 情绪与融入 | 怕问蠢问题丢脸 | 当心理疏导员 | ★★★ |

**结论：只做问答，最多解决第一条，导师照样嫌麻烦。** 工具必须把后四条也接过去。

---

## 2. 目标与非目标

### 2.1 目标

1. 新人**敢于提问、随时能问**，且答案**可追溯、不瞎编**。
2. 新人有一条**明确的成长路径**，自己知道下一步做什么、什么算过关。
3. 新人**有地方练手**并获得即时反馈，不必等导师有空。
4. 导师**从执行者变成审核者**：只看 AI 拿不准的、只看预警。
5. 知识**越用越厚**：新人问的问题自动沉淀成 FAQ，下一届更省事。

### 2.2 非目标（第一版明确不做）

- 不做绩效考核工具（会引发抵触，直接杀死使用率）。
- 不替代导师的判断与授权（权限、薪资、人事决策一律转人工）。
- 不做大而全的知识中台（第一版只服务一个团队 / 一届新人）。

---

## 3. 产品定位与三条设计原则

**定位：不是"问答机器人"，是"培养流程的执行者"。**

| 原则 | 含义 | 落地方式 |
|---|---|---|
| **可信优先** | 培养场景里幻觉是致命的，新人会把错的当标准 | 每个答案必须带出处；置信度低自动转人工 |
| **闭环沉淀** | 工具要越用越省力，而不是越用越忙 | 重复问题自动变成 FAQ 草稿，导师一键入库 |
| **双向可见** | 单方面监控必然引发反感 | 成长档案对新人本人完全可见 |

补充一条工程原则：**知识必须是纯文本文件**（Markdown / JSON），放在版本库目录里。
理由：导师能自己改、能 review、能追溯"这条知识是谁写的、什么时候该复核"。

## 4. 功能全景：三层 8 模块

```
┌─────────────────────── 新人侧 ───────────────────────┐
│ ① 首日引导 + 环境自检    ② 知识问答（带出处）          │
│ ③ 学习路径闯关           ④ 陪练室（角色扮演 + 评分）    │
│ ⑤ 作业 / 代码批改                                     │
└──────────────────────────────────────────────────────┘
┌─────────────────────── 导师侧 ───────────────────────┐
│ ⑥ 成长档案 + 能力雷达     ⑦ 导师看板（预警 / 待办）    │
└──────────────────────────────────────────────────────┘
┌────────────────────── 沉淀闭环 ──────────────────────┐
│ ⑧ 提问箱 → FAQ 自动沉淀 → 知识库更新 → 下一届更省事   │
└──────────────────────────────────────────────────────┘
```

### 模块说明

**① 首日引导 + 环境自检**
一键运行配置化检查项（命令是否存在 / 端口是否可达 / 路径是否存在 / 环境变量是否配置 / 文件是否就位），失败项直接给出修复步骤。
这是新人第一天最痛苦、而导师重复讲最多次的事，也是投入产出比最高的模块。

**② 知识问答（带出处）**
检索增强生成，答案必须附来源；命中不到就给"转人工"而不是硬编。
支持匿名提问（新人最怕问蠢问题），匿名问题同样进入沉淀闭环。

**③ 学习路径闯关**
培养计划变成关卡地图，每关 = `学 → 练 → 考`，考试达标才解锁下一关。
导师只需要**一次性定关卡**，不用重复讲。研发与非研发各一套地图，共用同一套引擎。

**④ 陪练室**
AI 扮演"客户 / 评审人 / 面试官 / 事故中的老板"，多轮对话，结束后按评分标准逐维度打分并给出改进建议。
消耗的是算力，不是导师的时间。

**⑤ 作业 / 代码批改**
给一份评分标准（rubric），AI 先批，标注"拿不准"的条目交给导师终审。
导师从"逐行看完"变成"只看标红的"。

**⑥ 成长档案 + 能力雷达**
从问答、闯关、陪练、批改四路数据自动累积能力分，生成雷达图与周报。
**档案对新人本人可见**，让他看到自己的成长曲线。

**⑦ 导师看板**
一屏看完：谁卡在哪一关几天了、谁连续追问了、哪些问题 AI 没答上来、待终审的批改有几条。
**导师必须比原来更省事，否则工具活不过一个月。**

**⑧ FAQ 自动沉淀**
同一问题被问 ≥2 次 → 自动生成 FAQ 草稿 → 导师确认 → 入库。
这是"越用越省力"的关键机制：第二年知识库更厚，导师更闲。

## 5. 核心机制设计

### 5.1 知识问答的可信链路

```
提问
 ├─ 1. 匿名化 / 记录提问意图
 ├─ 2. 检索：TF-IDF 余弦，**按段落建索引**，标题段权重 ×3，正文段 ×1
 │      （整篇做余弦会被长文档稀释：2000 字的 FAQ 里出现一次「周报」，
 │        余弦值会低到不可用；按段落匹配既准，也能直接定位到正确的那一段）
 ├─ 3. 双重门控（分数 + 词覆盖率）：
 │      覆盖率 ≥ 0.30 → 分数需 ≥ 0.9
 │      覆盖率 < 0.30 → 分数需 ≥ 1.6（问句里大量词文档根本没有，必须更谨慎）
 │      不达标 ─────────────────────► 转人工（并进入沉淀池）
 ├─ 4. 生成：
 │      未接入模型 ─► 直接返回知识原文 + 出处（可信优先）
 │      已接入模型 ─► 模型基于 Top-K 生成，强制标注 [1][2] 来源编号
 ├─ 5. 兜底规则（两档，区别很重要）：
 │      HARD（薪资/人事/法务/社保）──► 无条件转人工，知识库有也不答
 │      SOFT（权限/生产库/密钥/报销）─► 知识库有强匹配就照文档答 + 附敏感提醒；
 │                                     知识库没有才转人工
 └─ 6. 记录：命中 FAQ 则 hits+1；未命中则进入沉淀候选池
```

**为什么敏感话题要分两档？**
第一版把「权限」也放进了一刀切转人工的名单里，结果「怎么申请软件权限」——
一个公司 FAQ 里明明白白写了流程的问题——也被推给了导师。
这跟"减少导师重复劳动"的目标是反的。区分标准是：

- **答案依赖个人情况、答错不可逆** → HARD，必须真人（薪资、绩效、离职、社保、法务）。
- **公司有标准流程、照文档答就没错** → SOFT，照文档答并附出处，再提醒一句"动手前确认一次"。

**为什么是"分数 + 覆盖率"两个信号？**
纯词频分数有个致命毛病：问「会议室怎么预约」时，「会议」是个高频词，会让讲会议纪要的文档拿到 0.34 的高分——但问句里「预约」在全部文档中一次都没出现。覆盖率（问句里有多少比例的词在这篇文档里出现过）恰好能识别这种情况，所以低覆盖率时改用更高的门槛。

**实测标定结果**（30 条人工标注查询，见 `smoke_test.py` 与文档附录）：
「应转人工」的 10 条全部正确转人工，**零误答**；「应命中」的 20 条命中 18 条。
剩余 2 条走的是转人工 + 沉淀闭环——**失败方向是安全的**：宁可多问一句导师，也不给出可能错误的答案。

**为什么要有"未接入模型"这一档？** 因为小工具大概率一开始没有 API Key。
此时它必须仍然可用——退化成"带出处的知识库检索"，而不是一个转圈圈的废物。

### 5.2 关卡闯关与解锁

- 关卡状态：`locked` / `available` / `passed`
- 通关条件：该关考试得分 ≥ 关卡设定的 `pass_score`（默认 80）
- 前置依赖：上一关 `passed` 才解锁（线性），或由 `requires` 字段显式指定（可并行）
- 每次考试落下一条 `exam` 记录，用于雷达图打分与导师看板

### 5.3 能力雷达与档案

能力分四路数据合并：

| 能力维度 | 数据来源 |
|---|---|
| 业务理解 | 闯关考试中的业务/心智题得分 |
| 专业能力 | 闯关考试专业题得分 + 作业批改得分 |
| 协作沟通 | 陪练场景得分 |
| 规范意识 | 批改的规范类条目得分 + 环境自检通过率 |

**提问行为不参与能力打分。** 理由：用提问频次打分会诱导新人"少问问题"，与工具目标直接相反。
新人问了什么、有没有被答上来，只进入导师看板与沉淀池，不进入雷达图。

分数按 0–100 归一，最近记录加权更高（半衰权重 0.6，即越近的记录权重越大）。
**不做人与人之间的排名**，只做"个人 vs 岗位基线"，避免内卷式抵触。

### 5.4 陪练引擎

- 场景配置：角色、背景交代、开场白、评分标准、最大轮次
- 对话：带角色人设的多轮对话，未接入模型时退化为"结构化引导自省模式"
  （工具按评分标准逐条向新人提问，并给出自查清单——仍然有训练价值）
- 结束：按 rubric 逐维度 1–5 分 + 总评 + 三条具体改进建议 + 一段"导师会怎么答"

### 5.5 FAQ 自动沉淀闭环

```
新人提问 → 未命中知识库 → 进入沉淀候选池（按问题指纹聚类）
   → 同一意图累计 ≥2 次 → 生成 FAQ 草稿（含建议答案 + 待补出处）
   → 导师看板出现待办 → 一键确认 / 改写 → 状态 published → 进入检索池
```

问题指纹 = 去掉标点与停用词后的字符集合 Jaccard 相似度 > 0.6（第一版规则足够）。

### 5.6 环境自检

配置化检查项，四种类型，零依赖实现：

| type | 含义 | 关键字段 |
|---|---|---|
| `command` | 可执行命令是否可用 | `cmd`, `expect` |
| `path` | 路径/文件是否存在 | `path` |
| `env` | 环境变量是否配置 | `var` |
| `tcp` | 目标主机端口是否可达 | `host`, `port` |

每项带 `fix`（失败时展示的修复步骤）与 `required`（是否阻断后续）。

### 5.7 内容文件校验（必须有，不是锦上添花）

这个工具的前提是**导师用文本编辑器直接改内容文件**。由此带来一个隐蔽且危险的失败模式：

> `faq.json` 里少一个逗号 → JSON 解析失败 → 程序不崩，只是把 FAQ 当成空的加载了。
> 工具照常运行，只是"静默变傻"——新人问什么都说"知识库里没有"。

**静默失效比崩溃危险得多。** 所以必须主动检查并大声报出来：

- 服务启动时在控制台打印错误数与提醒数
- 页面侧边栏常驻提示，点进「设置」看完整清单
- 提供 `python check_data.py`，有错误时退出码为 1（可挂到提交前钩子）

校验覆盖：JSON 是否可解析、必填字段、id 重复、`answer` 是否是合法选项下标、
`dimension` 是否是引擎认识的四个维度之一、`requires` 是否指向存在的关卡、
`rubric` 引用是否存在、评分项权重合计是否为 100、`learn` 引用的知识条目是否存在。

同时做**编码容错**：Windows 记事本保存 UTF-8 默认会加 BOM，若不兼容，
导师"另存为"一次就会让整个文件失效。故所有内容文件按 `utf-8-sig / utf-16 / gbk` 依次尝试读取。

## 6. 系统架构

```
┌──────────────── 浏览器（原生 HTML/CSS/JS，无构建） ────────────────┐
│  问答 │ 成长地图 │ 陪练室 │ 作业批改 │ 我的档案 │ 导师看板 │ 知识库 │ 环境自检 │
└───────────────────────────────┬──────────────────────────────────┘
                                │  JSON over HTTP
┌───────────────────────────────▼──────────────────────────────────┐
│  server.py   纯 Python 标准库 HTTP 服务（http.server）              │
│  ├── 路由 / 静态资源 / JSON 序列化                                 │
│  └── core.py                                                      │
│      ├── Config     路径、阈值、LLM 配置                            │
│      ├── Store      SQLite：用户、问答记录、进度、成绩、沉淀候选       │
│      ├── KB         知识条目 + FAQ 加载、BM25 检索、出处回溯          │
│      ├── LLM         可选适配（OpenAI 兼容 / 未配置时降级）           │
│      └── agents.py  八个模块的业务逻辑                              │
└───────────────────────────────┬──────────────────────────────────┘
                                │ 纯文本文件（可 git 版本管理）
┌───────────────────────────────▼──────────────────────────────────┐
│  data/knowledge/*.md        知识条目（带 frontmatter：owner/复核日期）│
│  data/faq.json              已发布 FAQ + 草稿                       │
│  data/paths/*.json          关卡地图（研发 / 非研发）                │
│  data/scenarios/*.json      陪练场景                                │
│  data/rubrics/*.json        评分标准                                │
│  data/env_checks/*.json     环境自检项                              │
│  data/dimensions.json       能力维度与岗位基线                       │
│  data/runtime/mentor.db     运行数据（SQLite，不入库）               │
└──────────────────────────────────────────────────────────────────┘
```

**为什么是纯标准库？**
小工具要能在任何一台内网机器上活下来。`python server.py` 就能跑，不需要 pip、不需要 Node、不需要构建。
需要接大模型时，填一个 OpenAI 兼容的 Base URL + Key 即可，用 `urllib` 直连，依然零依赖。

## 7. 数据结构（Schema）

### 7.1 知识条目 `data/knowledge/*.md`

```markdown
---
id: kb-eng-001
title: 开发环境搭建与自检
track: engineering, general      # 逗号分隔
tags: 环境, 工具链, 第一天
owner: 张伟                       # 知识责任人，过期由他复核
review_date: 2026-06-30          # 复核日期，到期提醒
source: 内部 Wiki / 工程规范 v2
---

正文（Markdown）。支持小标题、列表、代码块。
```

### 7.2 FAQ `data/faq.json`

```json
{
  "items": [
    {
      "id": "faq-001",
      "q": "公司 WiFi 怎么连？",
      "a": "……",
      "track": ["general"],
      "tags": ["IT"],
      "owner": "IT 支持",
      "review_date": "2026-06-30",
      "source": "IT 手册",
      "status": "published",
      "hits": 0,
      "created_by": "seed"
    }
  ]
}
```

`status`：`published`（进入检索池）｜`draft`（待导师确认）｜`escalated`（转人工记录）

### 7.3 关卡地图 `data/paths/*.json`

```json
{
  "id": "engineering",
  "name": "研发新人 90 天成长地图",
  "track": "engineering",
  "stages": [
    {
      "id": "e1",
      "name": "第 1 关 · 环境与工具链",
      "window": "Day 1-3",
      "goal": "能独立跑通本地环境，遇到报错会查自检清单",
      "requires": [],
      "learn": [{ "title": "开发环境搭建", "type": "kb", "ref": "kb-eng-001", "minutes": 30 }],
      "practice": [{ "title": "运行环境自检", "type": "env_check", "ref": "engineering" }],
      "exam": {
        "pass_score": 80,
        "questions": [
          {
            "id": "e1q1",
            "q": "题干",
            "options": ["A", "B", "C", "D"],
            "answer": 0,
            "dimension": "business",
            "explain": "解析"
          }
        ]
      }
    }
  ]
}
```

`dimension` 取值对应 `dimensions.json`：`business` / `professional` / `communication` / `discipline`

### 7.4 陪练场景 `data/scenarios/*.json`

```json
{
  "id": "sc-eng-review",
  "name": "代码评审答辩",
  "track": ["engineering"],
  "difficulty": 3,
  "rubric": "code-review",
  "role": "资深工程师（你的评审人）",
  "brief": "你提交的 PR 收到了 3 条评审意见，现在要在 5 分钟内说清楚你的设计取舍。",
  "opening": "我看了一下你的 PR。先说说你为什么把这块逻辑抽成独立服务？",
  "max_turns": 6,
  "coach_tips": ["先讲结论再讲理由", "承认不确定的地方比硬撑更加分"]
}
```

### 7.5 评分标准 `data/rubrics/*.json`

```json
{
  "id": "code-review",
  "name": "代码评审答辩评分标准",
  "items": [
    {
      "id": "structure",
      "name": "表达结构",
      "weight": 25,
      "levels": { "1": "想到哪说到哪", "3": "有条理但缺重点", "5": "结论先行、层次清晰" }
    }
  ]
}
```

### 7.6 能力维度 `data/dimensions.json`

```json
{
  "dimensions": [
    {
      "id": "professional",
      "name": "专业能力",
      "baseline": 70,
      "anchors": { "1": "需要手把手", "3": "能独立完成常规任务", "5": "能设计并兜底" }

  ]

```


## 9. 运行方式

```powershell
cd ai-mentor
python server.py            # 默认 http://127.0.0.1:8848
python server.py --port 9000
python server.py --host 0.0.0.0   # 让同一局域网内的同事访问
```

自检：

```powershell
python check_data.py        # 校验全部内容文件（改完知识库后跑一下）
python smoke_test.py        # 端到端冒烟测试，需先启动服务
```

重置所有运行数据（问答记录、进度、沉淀池）：

```powershell
Remove-Item data\runtime -Recurse -Force
```

接大模型（可选，不填也能用，退化为带出处的知识检索）：

```powershell
$env:MENTOR_LLM_BASE_URL="https://api.deepseek.com/v1"
$env:MENTOR_LLM_API_KEY="sk-xxxx"
$env:MENTOR_LLM_MODEL="deepseek-chat"
python server.py
```

或在页面「设置」里填写，保存在 `data/runtime/settings.json`。

## 10. 落地路线图与验收指标

| 阶段 | 时间 | 交付 | 目的 |
|---|---|---|---|
| MVP | 3 天 | 50 条 FAQ + 环境自检 + 问答入口 | 先在 1 个新人身上验证 |
| V1 | 第 1–2 周 | 关卡地图 + 成长档案 | 让新人自己知道下一步 |
| V2 | 第 3–4 周 | 陪练室 + 作业批改 | 接住"陪练反馈"这条重复劳动 |
| V3 | 之后 | 导师看板预警 + 沉淀闭环自动化 + 飞书/企微机器人 | 让导师彻底从执行者变审核者 |

### 验收指标（拿这三个数去跟导师汇报）

1. **导师每周被重复提问的次数** —— 目标下降 70%
2. **新人从入职到能独立交付首个任务的天数** —— 目标缩短 30%
3. **知识库自动沉淀的条目数** —— 每届 ≥ 50 条

### 从零整理知识的三天手册（材料为空白时的做法）

- **第 1 天上午**：坐在导师旁边，把他过去半年被新人问过的问题全部记下来（翻聊天记录最快），目标 50 条。
- **第 1 天下午**：写成 `faq.json`，每条补 owner 与复核日期。宁可写短、写糙，别追求完美。
- **第 2 天**：把 3 件最烦的手工活变成自检脚本 / 批改 rubric / 陪练场景。
- **第 3 天**：找一个新人真实使用一天，记录"AI 没答上来的问题" —— 那就是下一批知识条目。

## 11. 风险与对策

| 风险 | 后果 | 对策 |
|---|---|---|
| 模型幻觉 | 新人把错误当标准 | 强制出处；双重门控（分数 + 覆盖率）；兜底转人工；敏感话题两档处理 |
| **内容文件静默失效** | 打错一个逗号，工具"静默变傻"却看不出异常 | 启动时校验 + 页面常驻提示 + `check_data.py`；编码容错（BOM/UTF-16/GBK） |
| 知识过期 | 半年后开始教错东西 | 每条知识带 owner + review_date，过期在导师看板预警 |
| 新人反感被监控 | 抵触、不说真话 | 档案双向可见；不做人际排名；提问支持匿名；提问不参与打分 |
| 导师不买账 | 工具自然死亡 | 导师侧必须更省事（一屏看板 + 只看标红项）；不增加导师任何录入负担 |
| 敏感规则一刀切 | 有标准答案的流程问题也被推给导师 | 分 HARD / SOFT 两档，SOFT 档照文档答并附提醒 |
| 冷启动没内容 | 新人问三句就不用了 | 先用 FAQ 撑住前 50 个高频问题；未答问题自动进沉淀池 |
| 贪大求全 | 三个月做不完 | 严格按路线图，先做导师最烦的 3 件事 |

## 附录 A · 检索阈值标定明细

阈值不是拍脑袋定的，是用 30 条人工标注的查询实测出来的。改动任何检索参数后，
`smoke_test.py` 里的「检索标定回归」段落会立刻告诉你有没有调坏。

**标定方法**：准备 20 条"应该命中"的真实新人提问 + 10 条"知识库里根本没有"的问题，
打印每条查询的余弦分数与词覆盖率，找到能把两组分开的判定规则。

**实测数据（节选）**

| 查询 | 分段余弦 | 词覆盖率 | 判定 |
|---|---|---|---|
| 试用期考核主要看什么 | 2.84 | 1.00 | 命中（强） |
| 怎么申请软件权限 | 2.17 | 0.83 | 命中（强） |
| 开发环境怎么搭建？ | 1.91 | 0.67 | 命中（强） |
| 转正流程是什么 | 1.49 | 0.60 | 命中 |
| 会议纪要要写什么 | 1.28 | 0.33 | 命中（附提醒） |
| 线上出事故了怎么办 | 1.27 | 0.40 | 命中 |
| **会议室怎么预约** | **1.46** | **0.20** | **转人工** ← 分数不低，靠覆盖率拦下 |
| Git 分支怎么命名 | 0.72 | 0.60 | 转人工（已知漏召，走沉淀闭环） |
| 周报要写什么内容 | 0.28 | 0.17 | 转人工（已知漏召，走沉淀闭环） |
| 今天食堂中午有什么菜 | 0.23 | 0.14 | 转人工 |
| 公司股票代码是多少 | 0.68 | 0.12 | 转人工 |
| 年会在哪个酒店办 | 0.31 | 0.17 | 转人工 |

**最终规则**

```
need = 0.9  当 覆盖率 ≥ 0.30
need = 1.6  当 覆盖率 <  0.30
分数 < need  →  转人工并进入沉淀池
```

**结果**：10 条"应转人工"全部正确转人工（**零误答**），20 条"应命中"命中 18 条。
漏掉的 2 条（周报、Git 分支命名）走的是转人工 + 沉淀闭环——
**失败方向是安全的**：宁可多问一句导师，也不给出可能错误的答案。
这两条也正是沉淀闭环要解决的典型样本：被问两次之后，它们就会变成 FAQ。

**为什么不能只用分数？** 「会议室怎么预约」的分数（1.46）比两条正确命中的还高。
原因是"会议"是高频词，让讲会议纪要的文档拿到了高分，而问句里的"预约"在全部文档中一次都没出现。
覆盖率恰好能识别这种情况——这就是需要第二个信号的原因。

> ⚠️ 这份标定基于当前 8 条知识 + 20 条 FAQ 的小样本。
> 知识库扩到几百条后，建议重新跑一遍标定，或直接换成向量检索 + 重排模型。
